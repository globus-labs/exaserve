For build_openai_app, does router replica scales with the model replica?
Default behavior: auto-scales with model replicas
When num_router_replicas is not set, the router uses autoscaling tied to your model replicas via a 2x ratio:
Parameter	Default	Source
min_replicas	model_min_replicas * 2	0 * 2 = 0 for you
initial_replicas	model_initial_replicas * 2	1 * 2 = 2 for you
max_replicas	model_max_replicas * 2	2 * 2 = 4 for you
target_ongoing_requests	100	per router replica
So yes, it scales automatically: if you increase max_replicas to 6 for your model, the router max goes to 12. The autoscaler adds/removes router replicas based on request load (target_ongoing_requests).
When num_router_replicas is set, it becomes static — min/initial/max are all pinned to that value, disabling autoscaling.
No built-in placement control
There is no ray_actor_options or placement strategy on the router deployment. Ray Serve uses its default scheduling, which spreads replicas across nodes that have available CPU resources. It doesn't guarantee even distribution — it's best-effort based on resource availability. Since routers are CPU-only (no GPU), they'll land on whichever nodes have free CPU slots.
You can also tune via environment variables
From the constants file, these env vars override defaults without touching code:

RAY_SERVE_LLM_ROUTER_TO_MODEL_REPLICA_RATIO=2    # default 2x
RAY_SERVE_LLM_ROUTER_MIN_REPLICAS=0               # default 0
RAY_SERVE_LLM_ROUTER_INITIAL_REPLICAS=2            # default 2
RAY_SERVE_LLM_ROUTER_MAX_REPLICAS=16               # default 16
RAY_SERVE_LLM_ROUTER_TARGET_ONGOING_REQUESTS=100   # autoscale trigger

GPU OOM Problem
The error is not about 64 GB being insufficient for an 8B model. The model only needs ~15 GB per tile. The real culprit is concurrent vLLM memory profiling across tiles sharing the same PVC card.
During startup, all 12 EngineCore subprocesses simultaneously run a dummy forward pass (profile_run()) to measure available GPU memory. This triggers concurrent SYCL kernel JIT compilation on pairs of tiles that share a physical PVC card. The Level Zero driver, under this concurrent load, reports massively inflated "non-torch" memory usage on some tiles:
Healthy tiles: ~3 GB non-torch memory (correct)
Affected tiles: 31-47 GB non-torch memory (erroneous)
This inflated measurement makes vLLM think available_kv_cache_memory = 65520 * 0.95 - 62762 = -518 MB (negative), which triggers the error. The affected tiles are consistently the second tile on a PVC card (tiles 1, 7, 9, 11 in your run), confirming the card-level resource contention theory.
Fix (two layers)
Staggered initialization (primary) -- Odd-numbered tiles (the second tile on each PVC card) now sleep for 20 seconds before starting engine init. This ensures the two tiles on each card don't run their memory profiling simultaneously. Configurable via INIT_STAGGER_SECONDS env var.
Retry logic (safety net) -- If engine creation still fails (e.g., model-loading times vary enough to re-create overlap), the worker retries up to 3 times with increasing back-off delays. Configurable via ENGINE_INIT_RETRIES.
The total startup overhead is ~20 seconds (one stagger wave), which is small relative to the ~2 minute model loading time.

Ray's Locality Aware approach
On the 3rd approach: Locality-Aware Routing (reducing replicas visible to a single proxy)
This is the most architecturally interesting mitigation, and potentially the most impactful for large-scale deployments.
The fundamental problem
Ray Serve uses a single ProxyActor per node that acts as both the HTTP ingress and the load balancer. By default, when a request arrives, the proxy queries all replicas cluster-wide to get queue lengths, then routes to the least-loaded one. At 64 nodes × 12 tiles = 768 replicas, the proxy is sending 768 concurrent RPCs every time it needs to make a routing decision. That's O(N) work per request.
What locality-aware routing would do
Instead of each proxy polling all 768 replicas, you'd partition replicas so each proxy only "sees" (and polls) the replicas on its own node or a small subset of nearby nodes. For example, with 12 replicas per node, a proxy only queries 12 replicas instead of 768 — a 64x reduction in polling overhead.
Two ways to achieve this with your setup
Option A: Ray Serve's built-in locality_enabled routing (simplest)
Ray Serve has a locality_enabled setting in its routing config. When enabled, the proxy prefers replicas on the same node before going remote:
serve.run(    deployment,    route_prefix="/",    _local_node_routing_enabled=True,   # or via serve config YAML)
However, this is a soft preference, not strict locality — if the local node is saturated, it will still go remote. It also doesn't eliminate the global polling problem entirely.
Option B: Explicit per-node deployment sharding (more robust)
You could restructure your deployment so that instead of one large deployment with 768 replicas all talking through a single ingress, you run one deployment per node (or per rack) and use your own request routing at the client or load-balancer level:
Client → node-local HTTP proxy → VLLMWorker replicas on that node only
In your current architecture, this would mean something like:
Each node runs its own exaserve_serve.py with num_replicas=12 (local tiles only)
The client driver (your replay_client.py) distributes requests across nodes itself (round-robin, random, or by tracking per-node load via a lightweight sidecar)
This is essentially what your system already does per-node — the issue is that Ray Serve then federates all of them under one global proxy which reintroduces the O(N-replicas) polling.
Why this is the long-term right answer
The 0.1s polling deadline and the NoneType bug are both symptoms of Ray Serve not being designed for O(100s) of replicas behind a single proxy. Increasing the deadline to 2s (mitigation 1) trades latency headroom for correctness, but as you scale further, even 2s will eventually be insufficient. Sharding the routing keeps the per-proxy replica count constant regardless of total cluster size, giving you true O(1) routing overhead per request.
For your null-compute experiment specifically at 64 nodes, the simpler fix (the 2.0s deadline just applied) should be sufficient. But if you plan to go to 128+ nodes, the sharding approach is worth pursuing.

Why ray is not scaling? Why ray errors out at 2048 nodes?
The Real Problem: serve.run() Deployment Time Exceeds the 20-Minute Timeout
The actual failure is that serve.run() (line 509 of exaserve_serve.py) blocks until all replicas report as RUNNING. With 24,576 replicas (2048 nodes × 12 tiles), this deployment takes far longer than the driver's 20-minute timeout (240 retries × 5s = 1200s). The deployment time scales roughly linearly (possibly super-linearly) with replica count:
Nodes	Replicas	serve.run() Time	Status
256	3,072	99.58s (~1.7 min)	Success
512	6,144	198.99s (~3.3 min)	Success
1024	12,288	1240.64s (~20.7 min)	Barely succeeded
2048	24,576	>1200s (killed at timeout)	Failed all 3 attempts
Notice the scaling is super-linear: 256→512 doubles replicas and doubles time (linear), but 512→1024 doubles replicas and the time jumps 6.2x (from 199s to 1241s). This strongly suggests the Ray GCS/ServeController becomes a bottleneck at this scale. All 3 attempts for 2048 nodes failed identically:
Attempt 1 (23:21:45): Detected 24,552 GPUs → timeout at 20 min
Attempt 2 (23:41:45): Detected 24,576 GPUs → timeout at 20 min
Attempt 3 (00:02:01): Detected 24,576 GPUs → timeout at 20 min
In each attempt, only about ~12,900 of the 24,576 replicas managed to initialize before the driver killed the process.
Why serve.run() Blows Up at Scale
The Ray Serve ServeController is a single actor on the head node that must:
Request 24,576 actor placements from GCS (one round-trip per actor)
Track health status of all 24,576 actors
Update the routing table for 2,048 proxy actors (ProxyLocation.EveryNode)
Process health check responses from all replicas
At 24K replicas, the controller becomes CPU-bound managing the actor lifecycle state machine. The GCS (also a single process on the head node) is also overloaded processing placement requests. This is a known Ray Serve scaling limitation — the controller is not designed for O(10K) replicas.
Potential Fixes
There are a few approaches you could consider (switch to Agent mode if you want me to implement any):
Increase the driver timeout: Set MAX_RETRIES higher. 1024 nodes barely fit in 20 minutes. 2048 nodes would likely need ~40-60 minutes. But this is a band-aid — the super-linear scaling suggests 4096 nodes would be impractical.
Batch the deployment: Instead of deploying all 24,576 replicas in a single serve.run() call, deploy in waves (e.g., scale up num_replicas incrementally). Ray Serve supports updating num_replicas on a running deployment.
Reduce replicas per node: If you don't need all 12 tiles active, using fewer replicas reduces the controller's burden.
Use multiple independent Ray Serve applications: Instead of one deployment with 24,576 replicas, deploy node-local services where each node runs its own independent serve instance. This eliminates the centralized controller bottleneck entirely.

Root Cause of AttributeError: 'NoneType' object has no attribute 'routing_context' <- "if not pending_request.routing_context.should_backoff"
This is a bug in Ray Serve's _choose_replicas_with_backoff generator — specifically a missing null check at line 943 of request_router.py.
The crash path
Step 1: _fulfill_pending_requests (line 980) calls _get_next_pending_request_to_route(), which can return None when _pending_requests_to_route is empty — either because the queue is exhausted or all queued futures are already done:
request_router.py
Lines 884-892
```
def _get_next_pending_request_to_route(    self,) -> Optional[PendingRequest]:    
    while len(self._pending_requests_to_route) > 0:        
        pr = self._pending_requests_to_route.popleft()        
            if not pr.future.done():            
                return pr    
    return None
```
Step 2: That None is passed directly into _choose_replicas_with_backoff(None) (line 982–984).
Step 3: Inside the generator, choose_replicas(pending_request=None) is called. It properly handles None — in pow_2_router.py it guards with if pending_request is not None, falling through to apply_locality_routing(None). And apply_locality_routing explicitly handles None by returning all replicas:
request_router.py
Lines 136-137
        if not pending_request:            
            return self._replica_id_set
Step 4: Since there ARE replicas (they're just full/busy, not absent), choose_replicas returns a non-empty candidate list. The generator yields those candidates back.
Step 5: Then the generator reaches line 943 with pending_request still None:
request_router.py
Lines 943-944
```
                if not pending_request.routing_context.should_backoff:                    
                    continue
```
Crash. pending_request is None, so pending_request.routing_context raises AttributeError: 'NoneType' object has no attribute 'routing_context'.
Why small max_ongoing_requests triggers this
With a small max_ongoing_requests, all replicas are saturated rapidly. The routing system is constantly looping in backoff, cycling through _choose_replicas_with_backoff at high frequency. 
There are also potentially multiple routing tasks running concurrently (controlled by target_num_routing_tasks). Each task calls _get_next_pending_request_to_route() which pops from the shared _pending_requests_to_route deque. 
When there are more active routing tasks than queued requests, some tasks get None back. Those tasks then crash at line 943.
It repeats 140 times because the finally block in _fulfill_pending_requests (line 1026) removes the crashed task from _routing_tasks, which triggers _maybe_start_routing_tasks to spawn a replacement, which immediately gets None again and crashes again, in a tight loop.
The fix (conceptually)
The missing guard should be at the start of the backoff check in the generator — something like:
if pending_request is None or not pending_request.routing_context.should_backoff:    continue
Or alternatively, the outer loop in _fulfill_pending_requests should not enter _choose_replicas_with_backoff when pending_request is None.
